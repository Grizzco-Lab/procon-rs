# CLAUDE.md

- Do not add any unused packages
- Add and remove dependencies with `cargo add` / `cargo rm` (-F for features; no unused features). Editing Cargo.toml by hand is fine for what cargo cannot do (feature groups, workspace settings, cleanup). Never edit Cargo.lock by hand.
- Call `cargo fmt` to format the code after finish editing. Use `prettier` for html.
- All the comments and docs must be in English. Chinese should never appear in the code. (The one exception is the page's Simplified Chinese dictionary, `crates/grizzco-lab/web/i18n-zh.js`, which is data.)
- Keep it simple.
- rust has great inline doc feature (/// to struct, member, functions, and //! to the top of the file). You should leverage it as if you're really writing rust.
- follow what's there in the code; do not hallucinate.
- use core/alloc instead of std whenever possible. (I think this practice is good)

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Grizzco Lab (until 2026-09-29 ProCon Studio) records Nintendo Switch gameplay for training datasets: Pro Controller input, timestamped, next to the console's video and sound. The README is the user guide; CONTRIBUTING.md has the same architecture in more words; `doc/index.html` is the illustrated write-up (screenshots in `doc/images/`, hero image `doc/demo.png`); `doc/story.html` is the project's story in English and Chinese (ideas, decisions, dead ends and optimisations, chapter by chapter, with a new chapter after each major milestone: its end says how), its videos `doc/story/<scene>-<lang>.mp4` rendered from the page's own canvas scenes by `node doc/story/render.mjs [scene]` (headless Chrome, ffmpeg).

The root `Cargo.toml` is a virtual workspace; every package is a crate under `crates/` (the repository keeps the name procon-rs for now; the user renames it later):

- `procon-proxy` (`crates/procon-proxy`, config `proxy.toml`): USB proxy on a Raspberry Pi 4 between the Pro Controller and the Switch (USB gadget); streams timestamped frames over TCP (`[stream] port`, 7331) and takes replayed actions (`[replay] port`, 7332); resets the controller at start.
- `procon-core` (`crates/procon-core`): what the proxy and the lab share, so the proxy never builds the lab's crates: frames and dumpers (`dump`), session folders with `controller.bin` (`recorder`), the frame link (`stream`), replayed actions and the replay port (`replay`), and the TOML loader with the `[logging]` section (`config`).
- `grizzco-lab` (`crates/grizzco-lab`, config `config.toml`): Grizzco Lab on the Linux host with the capture card, each app a module of it (`src/studio`, `src/inspect`, `src/cuttlefish`, `src/vision`, `src/predictor`, `src/pipeline.rs`; `src/web.rs` serves the page from `web/` and every app's routes). Web dashboard with six apps: Studio (live preview, controller view incl. 3D, recording with sound and game settings, technique markers, replay, data, motion), Inkspector (recorded sessions frame by frame: labels, delays, sound, overlays, predictions, object labeling), Cuttlefish (a chat with the AI reviewer, saved in reviews; VOD reviews with comments and drawings; a Translate view for jargon over the glossary; a Knowledge view managing the `cuttlefish` store), Vision (detection and tracking with `gameplay-vision` through our classes, dataset overview, send to labels), Predictor (AgentZero's IDM on any video, its predictions against the truth; AgentZero's policy online, on a video or on the live capture, where it can play the Switch) and Pipeline (both machines side by side and alike, this host and the win11 VM, and the experiment queue, live: what runs on each GPU with its progress and loss, each machine's vitals, what waits in the order the user drags it into, results and history). Every project is used from the page, not the CLI.
- `crates/gameplay-data`: recording format, per-frame alignment, labels, calibration, the true camera turn (AgentZero's per-session fits); Python bindings (`python` feature, maturin) used by the AgentZero training project (`../AgentZero`, which builds it from `../procon-rs/crates/gameplay-data`: keep it there).
- `crates/gameplay-vision`: object detection (YOLOv8 in candle, CPU; `cuda` feature) and SORT-like tracking on session video, the object label files shared with the labeling tool (`<annotations>/<session>/<segment>.objects.jsonl`, `classes.json`) and prelabeling; `hud`: the Salmon Run HUD (wave, timer, eggs) read from any video by blobs and template matching (`src/hud/templates.txt`, learned from our sessions' countdowns and, for waves 4 and 5, Eggstra Work in Azu's streams; egg counts of 100 and up stretched before matching), and the timer's physics into a per-video `wave_starts.json` with `to_video_time(wave, timer_s)`; CLI `gameplay-vision` (`detect`, `track`, `prelabel`, `render`, `hud scan|read|time|learn`). ## Architecture

**Proxy side** (`crates/procon-proxy`)
- `src/device.rs`: the physical controller through hidapi; waits for it as long as it takes. `device::reset()` replugs it through sysfs (`authorized` 0/1) at proxy start: a controller the console knows over Bluetooth connects wirelessly when idle, which stalls the USB handshake (Switch stops after `subcommand 03`). Do not change its polling interval (`usbhid.jspoll`): on the Pi 4 it breaks the output endpoint and the Switch's handshake.
- `src/gadget.rs`: USB gadget (usb-gadget crate) with the Pro Controller's IDs; returns the `/dev/hidg*` path.
- `src/proxy.rs`: input (controller → Switch) and output (Switch → controller: rumble, LEDs, subcommands) on separate threads; a write to the controller blocks ~9 ms and the Switch sends rumble constantly. Each frame's `forward_us` is the time from reading the report to the Switch taking it (poll POLLOUT on the gadget); the dashboard shows it as the "Proxy +x ms" chip.
- `src/wake.rs`: while the Switch sleeps, Home restarts the DWC2 clock (`PCGCTL.StopPclk`, which also freezes `DSTS`) and sets `DCTL.RmtWkUpSig` through `/dev/mem`, as the driver's `dwc2_gadget_exit_clock_gating` does. The Switch 2 ignores it; the original Switch is untested.
- `src/priority.rs`: nice -10, `SCHED_FIFO` 50 as root, optional CPU affinity (`[performance]`).

**Shared** (`crates/procon-core`, in both binaries)
- `src/dump.rs`: `Dumper` trait, `AsyncDumper` (own thread, drops on backpressure), `FileDumper`, `MultiDumper`; frames are `gameplay_data::frame::Frame`.
- `src/replay.rs`: JSON-line `Action`s, loaded from a session, `controller.bin` or `.jsonl`; the proxy's replay port applies the latest action to input reports (or, with `mix`, combines them: buttons OR-ed, each stick the controller's while pushed past `STICK_DEADZONE` (300 raw from 2048; the owner's sticks rest up to ~205 off it) and the gyro while turning faster than `GYRO_DEADZONE_DPS` (10 °/s), else the line's, so a person corrects it live; a line without sticks/gyro leaves them to the controller) before they are recorded and forwarded. A change here needs the proxy redeployed.
- `src/recorder.rs`: session folders `<prefix>YYYY-MM-DD_HH-MM-SS/` with `controller.bin`; start/pause/resume/stop.
- `src/stream.rs`: proxy-side `FrameStreamer` (TCP, 8-byte header then 80-byte frames, heartbeats after 1 s without reports) and lab-side `receive_frames` (sequence gaps as dropped frames, clock offset as the minimum `host_now - proxy_ts` over 10 s).
- `src/config.rs`: `load` and `LoggingConfig`; each binary's own sections are in its `src/config.rs`.

**Lab side** (`crates/grizzco-lab`; the paths below are in it)
- `src/studio/video.rs`: ffmpeg grabber (owns the input, raw 1080p frames; restarted only by choosing another input), preview encoder (low-latency H.264 as fragmented MP4, one fragment per frame, played by a `<video>`), one recording encoder per file (constant rate, keyframe every second). The grabber logs each frame's kernel capture time (`-ts mono2abs -copyts` + `showinfo`); recordings start at the first frame's capture time; a queue of late frames (>120 ms for 3 s while idle) restarts the grabber. A V4L2 capture card in YUYV (`v4l2_args` asking for no more than `-input_format yuyv422` and `-video_size`, `[video] v4l2_direct`, on by default) is read by the lab itself (`src/studio/v4l2.rs`: `Capture`, memory-mapped, `BUFFERS` = 4, `CLOCK_MONOTONIC` kernel timestamps, the ioctl structures checked against `linux/videodev2.h` at compile time; ffmpeg's v4l2 input asks for 256 buffers): `pump` hands the newest ready frame to the policy first, then puts every frame on the constant rate (`ConstantRate`, the fps filter's rule without holding a frame: the frame before repeats in skipped slots, a second frame for a slot is left out; the last frame keeps its buffer for repeats) into a converter ffmpeg (`converter_args`: YUYV in, the grabber's 1080p yuv420p out), with each frame's capture time queued for `read_frames`; open errors fall back to ffmpeg (`DIRECT_TRIES` in a row: ffmpeg until the input changes); the status's `direct` says which. `pump` counts the card's frames (`CaptureCounts` in `CaptureCounters`, over the lab's life: every frame, `corrupted` (corrupted or short, skipped) and `dropped` (gaps in the driver's sequence numbers); the frame before stands in for either on the constant rate, so no file gets a broken frame or loses its timing): the status's `capture` (`CaptureStatus`: since the reader started, `last_loss_ms`, and since the file being recorded started) feeds the Studio's chip, each file's own go to `session.json` per segment (`capture`, via `FileTimes::capture`; only when our reader read the card), and `LossLog` logs the first loss at once, then at most a line a `LOSS_LOG_EVERY` (60 s) with the count and rate per 1000 frames since the line before, so a start-up burst reads apart from a steady loss. `watch_first_frame`'s reopen after `FIRST_FRAME_TIMEOUT` is the Elgato 4K X's every-other-start quirk. The Predictor's live policy gets its own frames (`PolicySink`: YUYV of their size, `POLICY_FPS` 30, the newest, a frame once `policy_gap_ns` passed, split off before the constant rate, which holds each frame until the next one), from our reader or from ffmpeg's second output (`pipe:3`, `-filter_complex`: split after the 16:9 fit, `select` on `prev_selected_t`, `format=yuyv422`, `settb=AVTB` so the muxer never drops a frame for a repeated time, `showinfo@policy` times, `read_policy_frames`, always drained); `PolicyTimes` on `CLOCK_MONOTONIC` (`mono_ns`). Every raw output has `-threads 1` (ffmpeg's rawvideo encoder is frame threaded: 1–2 frames held back) and every pipe of frames is grown to 1 MiB (`grow_pipe`; 4 MiB fails for users, the default 64 KiB takes 48 hand-offs a 1080p frame). The first frame of a grabber clears the error of its retries. The input may be a video file: `-re -stream_loop -1`, stamped with the wall clock by `setpts=RTCTIME`, for testing without a console.
- `src/studio/audio.rs`: ffmpeg reads the `[video] audio_input` PulseAudio source continuously in 10 ms chunks (last 2 s kept); a recording's sound starts at the sample that arrived with its first frame and goes to the encoder on fd 3, as an Opus track in the same file.
- `src/studio.rs`: the Studio app (its parts in `src/studio/`), the coordinator; `Command`s from the dashboard, starts/stops recorder and video together, writes `session.json` (with `GameSettings`: Splatoon 3 sensitivities, which scale gyro/stick into camera turns, and `markers`), saves settings to the state file. Technique markers: `MarkStart`/`MarkStop` (the open span lives in `Session`; Pause/Stop end it), `MarkLast`, `MarkUndo`, `SetTechniques` (added techniques with their group in the state file); each marker has its `kind` (`technique`, `weapon`, `special`, `gameplay_data::session::MARKER_KINDS`) and `item` (the technique's id, or Lean's key of the weapon or special, `Shooter_Normal_Coop`), so AgentZero can count examples per weapon and special;
